Project Overview

Soqoni is a four-microservice e-commerce platform built as a hands-on DevOps portfolio project. Starting from bare application code, the platform was Dockerized, wired up with a full CI/CD pipeline, deployed to Kubernetes, migrated to managed cloud databases, and instrumented with an observability stack — demonstrating the full lifecycle of a production-grade cloud deployment.

System Architecture

The platform follows a microservices pattern with each service independently deployed, scaled, and monitored. Traffic enters through an nginx Ingress controller and is routed to the appropriate service based on path.

[ Architecture diagram — C2 Container View ]

Services

  • soqonifrontend — Node.js 20, serves UI + reverse proxies to backend
  • soqonicatalogue — Go 1.25, REST API for product catalogue
  • soqonicart — Java 17 / Spring Boot, shopping cart management

Infrastructure

  • Azure Kubernetes Service — managed control plane
  • Azure MySQL Flexible Server — catalogue database
  • Azure Cosmos DB (MongoDB API) — cart state
  • nginx Ingress + cert-manager — TLS termination

CI/CD Pipeline

Each service has a Jenkinsfile defining a four-stage pipeline: build the Docker image, run tests, package a release image using a multi-stage Dockerfile, then push a SHA-tagged image to Docker Hub. Images are never tagged :latest in Kubernetes manifests — every deployment references an immutable SHA tag to preserve rollback capability.

Jenkins Pipeline Stages

  • Build — compile + dev image
  • Test — unit tests (go test / Maven)
  • Package — multi-stage release image
  • Push — SHA-tagged image to Docker Hub

Kubernetes Deployment

  • Rolling updates — zero downtime deploys
  • HPA — CPU-based autoscaling (frontend: 2–5 replicas)
  • Resource requests & limits on all workloads
  • Liveness & readiness probes per service

Advanced Kubernetes — Traffic Management

Canary Deployment

A canary release was implemented for the catalogue service — routing 20% of traffic to a new image version while 80% continued on the stable version, verified by watching request distribution in Kiali before promoting the new version.

[ GIF: canary deployment — traffic split in Kiali ]

Fault Injection — HTTP Abort

Using Istio VirtualService fault injection, 50% of requests to the catalogue service were configured to return HTTP 500. The failure rate was observed live in Kiali's service graph, validating the resilience testing workflow.

[ GIF: fault injection — 50% HTTP 500, Kiali error rate spike ]

Fault Injection — Latency Delay

A 3-second artificial delay was injected into 100% of catalogue requests to simulate downstream degradation. Latency was visible in Kiali's distributed tracing view, demonstrating how a single slow service propagates to the frontend response time.

[ GIF: latency injection — 3s delay visible in Kiali tracing ]
